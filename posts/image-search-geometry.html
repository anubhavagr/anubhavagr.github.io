Image search is geometry before it is learning.

How "search by image" actually works — explained from zero, then stress-tested: I benchmarked five CNN backbones on the same FAISS pipeline, and every insight that mattered came from proofs and arithmetic, not from training.

TL;DR

Modern image search turns every picture into a vector, then finds nearby vectors. Once you see that, three things become provable rather than mystical: cosine and L2 similarity give identical rankings after normalization (two-line proof); precision 1.00 with recall 0.87 tells you exactly what kind of failure you have (ranking, not retrieval); and exact search dies on arithmetic you can do on paper (4×10⁸ distance computations per query at 100K images — 2.5% of that with an IVF index).

What this post is about

You've used Google Lens: photograph a shoe, get the same shoe back from a database of millions. That's content-based image retrieval (CBIR) — "search by what the image contains" rather than by text tags. The machinery is conceptually tiny:

  1. Turn each image into a vector (a list of ~1000 numbers) that summarizes its content.
  2. Store all the vectors in an index.
  3. To search: vectorize the query image, return the closest stored vectors.

This post is about everything that isn't step 1. The vectorization is learned (that's the ML); the rest is geometry and arithmetic — and the rest is where the real engineering decisions live. I'll cover:

  • what an embedding is and why "closer vector = similar image" is even coherent;
  • a two-line proof that the two similarity metrics everyone mentions — cosine and L2 distance — are the same thing;
  • how to read precision and recall for a retrieval system, and what their combination diagnoses;
  • the cost arithmetic that forces big systems away from exact search.

Prerequisites: vectors and dot products. No neural network knowledge needed — the one thing you have to take from deep learning (a CNN can produce a useful vector) is taken on faith and treated as a black box.

The project behind it

I built a small Lens-style search engine — find-me-lens — to understand the moving parts end to end. You point it at a folder of images organized by class, it embeds them all, and you can query with an image to get its nearest neighbors. The one product decision I cared about: which network produces the vector? So I ran five off-the-shelf CNNs — ResNet34, MobileNetV2, EfficientNet-B0, DenseNet121, InceptionV3 — through the identical pipeline. Same images, same index, same evaluation. Everything below comes from that experiment.

The vocabulary you'll need

  • Embedding: a vector (here, a few hundred to ~2000 numbers) representing an image, produced by the second-to-last layer of a neural network trained on image classification. The key property, which the training instills: images of similar things end up as nearby vectors. The network itself is called the backbone.
  • FAISS: Facebook AI Similarity Search — the standard open-source library for storing vector collections and answering "closest vectors to this one" quickly.
  • L2 normalization: dividing a vector by its own length, so all vectors live on a sphere of radius 1 (direction only, no magnitude).
  • Exact vs approximate search: exact = compare the query against every vector (perfect, expensive); approximate (e.g. the IVF index below) = compare against a clever subset (slightly imperfect, much cheaper).

The experiment, and its one table

Five backbones, one pipeline each: embed every image, index with FAISS, query with held-out images, and score the returned neighbors. Scoring needs one definition: a returned image counts as relevant if it belongs to the same class as the query. With that: precision = fraction of returned results that are relevant; recall = fraction of all relevant images in the database that you actually returned. Here's what came out:

Result 1: cosine and L2 are the same ranking

You'll see image-search codebases (including mine) normalize every vector to length 1 and then search by L2 distance — while every tutorial talks about cosine similarity. These produce identical rankings, and the proof is two lines of algebra.

Cosine similarity is the angle between two vectors, written cos θ where θ is that angle (1 = same direction, 0 = unrelated, −1 = opposite). Take two unit vectors a, b and expand the squared distance:

‖a − b‖² = ‖a‖² − 2a·b + ‖b‖² = 2 − 2·cos θ

Squared L2 distance is a strictly decreasing function of cosine similarity. Ranking by one is ranking by the other — no exceptions, no approximations. A few concrete pairs to build intuition for the mapping:

  • cos θ = 0.90 → distance² = 0.200
  • cos θ = 0.95 → distance² = 0.100
  • cos θ = 0.99 → distance² = 0.020

Two consequences. Practically: normalize once at index time and never think about metrics again. Conceptually: this picture is what a "good embedding" means — training doesn't magic similarity into numbers, it arranges directions on a sphere so similar images subtend small angles. Every retrieval metric you'll ever see is a measurement of that arrangement.

Result 2: P = 1.00 with R < 1 is a diagnosis

Back to the table's wall of perfect precisions. Recall the definitions — precision punishes wrong results returned; recall punishes right results missed. So P = 1.0000 for every backbone means: nothing wrong was ever returned. The neighborhoods are clean; no class ever leaked into another's results.

Then recall at 0.85–0.875 means: 12.5–15% of same-class images were not returned. Put the two together and the failure mode is pinned precisely: the missing neighbors exist in the index and are findable — they simply scored below the cut. All error is ranking error, none is confusion error.

Why does that distinction matter? Because it dictates the fix. If precision were the problem, you'd need a better backbone — the embeddings genuinely mix classes. With ranking-only error, the knobs are mechanical: return more neighbors per query, lower the similarity threshold, or improve within-class compactness (via fine-tuning). Compare two hypothetical systems with similar F1: P 0.90 / R 0.90 (confused embeddings — model problem) vs my P 1.00 / R 0.87 (conservative ranking — systems problem). Same F1, completely different to-do list. That's why I read the precision/recall pair shape before any single number.

Result 3: the arithmetic that kills exact search

My index is small, so it uses exact search: compare the query against every vector. That's a luxury, and the math says exactly how long it lasts. For a database of N images, each embedded into d dimensions:

  • Memory: N × d × 4 bytes. At a modest 100K images × 2048 dimensions: 819 MB of vectors (409 MB at half precision).
  • Compute per query: each distance is d multiply-adds; against every vector that's 2Nd ≈ 4.1 × 10⁸ operations. Per query. At 10M images it's 100× that.

Both scale linearly in N. No amount of GPU fixes linear. The standard escape is the IVF index: cluster the vectors into nlist cells once, offline; at query time, compare only against the nprobe cells nearest to the query. With the common heuristic nlist = √N and nprobe = 8, you touch 8√N vectors instead of N — 2.5% of the work at 100K images, 0.25% at 10M. The price is recall: a true neighbor sitting in an unprobed cell is missed. That price is tunable (raise nprobe toward exactness) and, importantly, measurable — which is why serious retrieval systems report "recall@k against exact search."

The left panel is the sleeper insight of the whole experiment: latency is decided by the backbone, not the search. The CNN forward pass dominates; FAISS is a rounding error. Which turns backbone choice into a quantified engineering decision: InceptionV3 buys +0.5 percentage points of recall over MobileNetV2 for 67% more latency. Take that trade or don't — but now it's a line item, not a benchmark trophy.

Same math, bigger scale

Everything above transfers unchanged to the LLM side of my day job. The RAG system I run at Griphic retrieves over 10K+ documents using 512-d embeddings of text instead of images: same normalization, same equivalence theorem, same recall-vs-cost dial on the index. Retrieval quality is a system property — metric definitions, index arithmetic, and the eval harness are the parts you own; the model is one ingredient.

Reproduce

git clone https://github.com/anubhavagr/find-me-lens
cd find-me-lens
pip install -r src/requirements.txt     # torch, torchvision, faiss

python src/prepare_database_all.py      # embed + index the image folder, all 5 backbones
python src/lens_all.py                  # query against the five FAISS indexes
python src/analysis.py                  # compare the backbones side by side

The comparison table above comes out of the analysis step. The convention throughout: a folder of images organized by class — that's all the pipeline assumes.
