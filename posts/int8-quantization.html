256 levels is plenty. Here's the math that proves it.

INT8 gets marketed as a trick. It's mostly bookkeeping — affine maps, error bounds, and one honest decision about outliers. The derivations, a calibration experiment where three objectives disagree on purpose, and the per-channel trick worth +6 dB.

TL;DR

An INT8 quantizer is an affine map with a provable s/2 error bound. The only real decision is where to clip — and I show that mean-squared error, bulk error, and entropy calibration pick three different thresholds for the same tensor on purpose. Quantize weights per output channel and the same 8 bits buy +6.1 dB SQNR. This is the machinery behind a product that runs at 600+ FPS inside a cath-lab.

The decision that started it

An X-ray enhancement network that a cardiologist waits on has a hard real-time budget. At FP32, the model was fast. "Fast" and "ships in the loop with the image acquisition system" are different requirements. The single highest-leverage change in the whole pipeline was also the smallest line item: cast the network to INT8.

Everyone eats the 4× memory reduction and the integer-kernel throughput and moves on. I want to slow down on the three pieces of math that decide whether those 256 levels are enough — because when someone asks "why is there no visual regression?", "TensorRT handled it" is not an answer.

1. The affine map, derived

Quantization maps a real interval to 2b integers. The standard asymmetric affine quantizer for signed activations picks a scale s and zero-point z so the range [xmin, xmax] covers all 256 codes exactly:

q = round(x / s) + z,    s = (xmax − xmin) / (2b − 1),    z = round(−xmin / s)

Why these? Demanding that xmin ↦ 0 and xmax ↦ 255 gives two equations in two unknowns; solve them and the formulas above fall out. Worked example from a real activation tensor with range [−2.1, 3.4]:

  • s = 5.5 / 255 ≈ 0.0216 — one code step is worth 0.0216 units
  • z = round(2.1 / 0.0216) = 97 — the code for the value 0

The error bound is now one line. Rounding contributes at most half a step, so |x − x̂| ≤ s/2 ≈ 0.0108, always, for every value in range. That's the entire "is 8 bits enough" calculation: compare s/2 against the smallest signal difference that matters downstream. For a network whose activations span units, thousandths of noise per element vanish in the sum over 3×3 receptive fields. They don't vanish for everyone — this is why INT4 needs care and INT8 usually doesn't.

And because both maps are affine, the conv y = w·x stays a pure integer op at run time — the scales fold into one output multiplier (sw·sx/sy) applied once. That folding is the whole reason integer kernels are worth building.

2. Calibration: pick an objective, get a threshold

Here's the part that is genuinely a decision, not bookkeeping. Real activations have a heavy bulk and a long tail. The quantizer's range [xmin, xmax] is chosen by calibration, and the naive choice — min–max over a calibration set — spends most of your 256 codes on values that almost never occur.

I built a synthetic post-GELU tensor with the shape that causes the trouble (99% of mass on [0, 4], smooth tail decaying to ~29) and ran three calibrators on it. Same tensor, same 256 codes, three different ranges:

The three objectives disagree, and each is right about something:

  • Full MSE picks min–max (28.9). This surprised me the first time I computed it: squared error weights rare far-outliers by their squared distance, so L2 always votes to keep the tail. The bulk pays: at this range, the 99%-mass region [0, 4] gets only 4/29 × 255 ≈ 35 distinct codes.
  • Bulk-99 MSE picks P99 (9.1). Measure error only where the mass lives and the optimum snaps to the 99th percentile. This is percentile calibration in one line of theory.
  • KL — entropy calibration — picks 7.0. Minimize the divergence between the reference and quantized distributions (1024-bin histograms, ε-smoothed). TensorRT's entropy calibrator is exactly this objective, and it lands near the bulk edge: the bulk gets ~4× more codes than under min–max.

The lesson I carry into production: calibration choice is a statement about which errors you tolerate. Our visual quality tracked distribution shape, not MSE — entropy calibration won. A robotics control head tracking small deltas might reasonably vote the other way. "Which calibrator did you use and why" is a question worth being able to answer from experiment, not from the default config.

3. Weights: the per-channel trick

Activations are dynamic — you calibrate them. Weights are known at build time, so you can do better: a separate scale per output channel. The reason it matters is visible in any trained conv tensor: channel magnitudes differ by an order of magnitude (11.8× spread in my synthetic replicate below), and one shared scale forces every channel to live inside the largest channel's range.

+6 dB is a factor of ~2 in RMS error, for zero latency cost — per-channel scales are constants folded into the kernel's output stage, not per-element work. This is also why "we tried INT8 and it broke" almost always means one of: min–max calibration on a skewed tensor, per-tensor weights, or both. The bits are rarely the problem; the range is.

On the production stack (PyTorch → ONNX → TensorRT, FastAPI/C++ serving), this combination — entropy calibration, per-channel weights, INT8/FP16 mix — is where 600+ FPS on an RTX 4090, a 70% latency cut, 35% lower VRAM, and <5% quality loss came from. The <5% is doing real work in that sentence: it's a measured perceptual comparison, and it's the number that made clinical sign-off possible.

One honest caveat to close the loop: if calibration can't find a range that works, the next tool is quantization-aware training — fake-quantize in the forward pass during fine-tuning and let the network learn weights that are happy on the integer grid (the straight-through estimator handles the non-differentiable round). We didn't need it here. Knowing it exists and when to reach for it is the difference between using a tool and understanding one.

Reproduce

The five-stage pipeline — PyTorch → ONNX → TensorRT → C++ — with one notebook per stage is on GitHub. The calibration and per-channel experiments above are ~40 lines of NumPy: sample a heavy-tailed tensor, sweep clip thresholds, and compute MSE / bulk-MSE / 10-bin-log KL per threshold. If your three objectives agree, your activations don't have a tail — check again with real data.
